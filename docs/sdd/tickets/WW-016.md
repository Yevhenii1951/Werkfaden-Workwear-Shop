# WW-016: Atomic quote acceptance (compare-and-set)

Status: implemented on branch `feature/ww-016-atomic-quote-accept` (uncommitted); `npm run check` + build green, red/green verified. Pending: commit, PR, fresh read-only review, merge.

## Intent / delivers

The B2B quote flow of WW-013 hands out money: accepting a quoted request
issues a single-use promotion code for the offered amount. The acceptance was
a read-then-write sequence (`retrieve` -> `create promotion` -> `update
status`), so two accepts that overlap in time both read the status "quoted",
both create a promotion and both report success. The buyer then holds two
valid codes for one offer.

This ticket makes the acceptance a compare-and-set: the quote row is moved
from "quoted" to "accepted" only while it still is "quoted". The request that
wins the row issues the code, every other request is rejected without
creating a promotion. The status change happens *before* the promotion is
created, so a failed promotion no longer leaves a code behind and the
compensation can hand the quote back to the buyer.

## Verification scenario

GIVEN a quoted request WHEN two accepts are sent at the same time THEN
exactly one succeeds, exactly one single-use code exists and the request
carries the code of the winner; the losing request is rejected and leaves no
promotion behind.

## Acceptance criteria

- The status change is a single conditional statement (`UPDATE ... WHERE id =
  ? AND status = 'quoted'`), not a read-then-write pair.
- The promotion is created only after the acceptance was won, so a rejected or
  failed accept creates no promotion.
- A failed workflow releases the reservation again: the quote returns to
  "quoted" and the stored code is cleared.
- Integration test on the isolated test DB: two concurrent accepts on one
  quoted request - exactly one success, one rejection, exactly one new
  promotion, and the stored `promotion_code` equals the code of the winner.
- Integration test on the isolated test DB: a failed workflow releases the
  reservation - the quote is "quoted" again, no promotion exists and a later
  accept succeeds.
- The existing WW-013 scenarios keep passing (single accept, second accept
  rejected, code applies once in the cart).
- `npm run check` green; build green; fresh read-only review recorded in the
  PR.

## Non-goals

No change to the quote status map, no company accounts, no price lists, no
quote PDF, no operator UI for quotes, no new promotion type.

## Known limits

- A crash between the reservation and the promotion leaves the quote
  "accepted" without a code. The status map does not allow an operator to
  re-quote an accepted request, so such a quote can only be closed; the buyer
  has to request a new quote. There is no recovery job in this demo scope.
- If the promotion is created but the workflow dies before the compensation
  runs, an unused promotion row stays behind. It is harmless: the code was
  never handed out, so nobody can use it.
