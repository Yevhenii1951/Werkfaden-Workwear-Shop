# WW-019: Private uploads stay private, decoded rasters stay bounded

Status: in progress (branch `fix/ww-019-private-uploads`).

Surface: `B` (backend config, upload module, tests).

## Intent / delivers

Closes the two findings of the 2026-10-25 review that concern the upload path.

**S1 — a private logo was public.** `medusa-config.ts` pointed both
`upload_dir` and `private_upload_dir` at `static/`. The framework serves
`static/` at `/static` for anonymous callers (`express-loader.js`), so a
submitted logo was readable by anyone who knew the file name; the `private-`
prefix is a naming convention, not an access control. Private files now go to
`private/`, which is not mounted anywhere. Only
`GET /admin/personalization-requests/:id/file` (admin-authenticated, streaming
from the provider, `Cache-Control: private, no-store`) hands them out.

**S3 — the 5 MiB limit did not bound the decode.** `decodeLogoRaster` decoded
the whole raster with sharp's default cap of 268 402 689 pixels. A 7000×7000
solid-colour PNG is under 1 MiB on disk and ~150 MB in memory, so the file
limit stopped nothing. The pipeline now runs with `limitInputPixels = 40 MP`
(A4 at 300 dpi is ~8.7 MP) and `sequentialRead`, and the raster is decoded
inside the same limited pipeline instead of a second unrestricted one.

## Blocked by

Nothing. WW-009 delivered the upload path this corrects.

## Verification scenario

GIVEN a public and a private upload WHEN both keys are requested at `/static`
THEN the public one is served and the private one is 404; and GIVEN a private
file WHEN an anonymous caller asks the admin download route THEN 401, WHEN an
admin asks THEN the exact bytes.

## Acceptance criteria

- `private_upload_dir` is a directory outside `static/`; `/private` is
  gitignored.
- Integration test `ww-019-private-uploads.spec.ts`: private file on disk under
  `private/`, absent under `static/`; `/static/<public key>` 200 (the mount is
  live, so the negative case is meaningful) and `/static/<private key>` 404;
  admin route 401 anonymous, 200 with correct `Cache-Control` and identical
  bytes for an admin.
- Unit test: an A5-at-300-dpi logo is accepted; a 7000×7000 PNG below 1 MiB is
  rejected with `MedusaError`.
- Existing personalization unit tests and the full `npm run check` stay green.
- Fresh read-only review of the diff before merge (uploads).

## Non-goals

No storage backend change, no presigned URLs, no virus scanning, no image
re-encoding, no new upload types, no admin UI.

## Known limits

- The local provider still returns a `url` for private files that now points to
  a 404. Nothing stores or renders that URL; the admin route reads by file id.
- Files uploaded before this change live in `static/`. Local demo data is moved
  once with `mv apps/backend/static/private-* apps/backend/private/`; a fresh
  install has no files to move.
- `limitInputPixels` protects the decode, not the upload bandwidth: multer
  still accepts up to 5 MiB before the raster is inspected.

## Checks / browser evidence

`npm run check`, `npm run build`, plus the two specs named above. The upload
path has no storefront surface of its own, so the browser scenario is the
existing `/personalization` form, unchanged.
