# WW-023: Setup aus dem Nichts reproduzierbar

Status: in progress (branch `chore/ww-023-reproducible-setup`).

Surface: `D` (Setup-Skripte, npm-Skripte, README/Handover).

## Intent / delivers

Found while judging the 2026-10-25 review: "first run" was not reproducible.
Concretely:

- Die dokumentierte Kette (`setup:env` → `db:migrate` → `setup:store` →
  `setup:checkout` → `setup:promotions`) säte weder Katalog noch Lagerbestände.
  Nach einer Anleitung, die man von oben nach unten ausführt, war der Shop
  leer — 0 Produkte, 0 Bestände, 0 Kollektionen.
- Für den Katalog-Seed gab es überhaupt kein npm-Skript; er existierte nur als
  Pfad in einem Kommentar.
- Die Ziel-Datenbank war in fünf Skripten als `/werkfaden_dev` fest verdrahtet.
  Eine zweite, saubere Datenbank (Probeinstallation, zweiter Demo-Shop) ließ
  sich damit nicht befüllen, und ein Tippfehler in `DATABASE_URL` wurde nicht
  geprüft, sondern nur die Zeichenkette verglichen.
- `setup-store` schrieb den Publishable Key unbedingt in
  `apps/storefront/.env.local`. Auf einer zweiten Datenbank hätte das die
  laufende Storefront auf den falschen Store gezeigt. Der Fehlerpfad war
  außerdem toter Code: der `throw` bei fehlender Key-Zeile landete im
  umgebenden `catch` und wurde zur Warnung.

Geliefert:

- `src/scripts/lib/isolated-db.ts` — `assertIsolatedLocalDb(action)` liest
  `DB_NAME` (Standard `werkfaden_dev`) und akzeptiert nur Loopback-Hosts mit
  exakt diesem Datenbanknamen. Alle Setup-Skripte rufen ihn auf.
- `src/scripts/setup-demo.ts` + `npm run setup:demo` — eine Kette:
  Store → Suchindex → Katalog → Bestand → Versand/Steuer/Zahlung → Rabattcodes.
  Jeder Schritt ist idempotent (find-or-create), die Kette ist wiederholbar.
- `src/scripts/prepare-search.ts` — füllt den Suchindex, bevor Produkte
  angelegt werden. Auf einer frisch migrierten Datenbank hat der Index noch
  keine aktive Version; der Seed scheiterte sonst pro Produkt mit einer roten
  Indexing-Meldung (und blieb folgenlos, weil der Index erst beim App-Start
  gefüllt wird). Nutzt `listIndexes()` / `reindex()` des Suchmoduls.
- `SETUP_WRITE_STOREFRONT_KEY=false` — überspringt das Schreiben des
  Publishable Key; die Warnung bei fehlender Key-Zeile ist jetzt ein echter
  Hinweis statt eines verschluckten Fehlers.
- `npm run setup:catalog` und `npm run setup:inventory` (fehlten), README- und
  Handover-Abschnitt neu geschrieben.
- `npm run backend:seed` entfernt: es rief `turbo seed --filter=@dtc/backend`
  auf, aber das Backend hat kein `seed`-Skript — der Befehl lief durch und tat
  stillschweigend nichts ("No tasks were executed"), obwohl die Anleitung ihn als
  Katalog-Seed nannte.
- `scripts/rehearse-demo-setup.sh` — legt eine Wegwerf-Datenbank an, migriert,
  fährt die Kette zweimal und vergleicht die Zeilenzahlen.

## Blocked by

Nichts. Der beim Probelauf gefundene Indexing-Fehler ist WW-027 und bereits
gemerged.

## Context to read

Dieses Ticket + ../contract.md (Modul-/Datenmodell) + ../handover.md. Medusa-
Fakten, geprüft gegen die installierte 2.21.2: `medusa exec` führt ein Skript
mit dem geladenen Container aus; `medusa db:migrate --execute-safe-search` legt
Index-Records an, füllt sie aber nicht; das Suchmodul bietet `listIndexes()`
und `reindex({ index })` (JSDoc in `@medusajs/types`).

## Verification scenario

GIVEN eine leere lokale Datenbank WHEN `db:migrate` und danach `setup:demo`
zweimal laufen THEN stehen nach beiden Läufen 25 Produkte, 150 Varianten,
5 Kategorien, 4 Promotions, 150 Bestände, 1 Region und 1 Versandoption in der
Datenbank, es steht kein Fehler im Log, und der Suchindex enthält 25 Dokumente.
GIVEN dieselbe Kette mit einer `DATABASE_URL`, die nicht zu `DB_NAME` passt
WHEN sie läuft THEN bricht sie vor dem ersten Schreibzugriff mit einer
verständlichen Meldung ab.

## Acceptance criteria

- `npm run setup:demo` richtet einen leeren Shop vollständig ein; ein zweiter
  Lauf ändert keine Zeilenzahl.
- Kein Setup-Skript schreibt ohne `assertIsolatedLocalDb`; der Guard liest
  `DB_NAME` und prüft Host + Datenbanknamen.
- Ein Fehlpaar aus `DATABASE_URL` und `DB_NAME` wird abgelehnt, die
  Entwicklungsdatenbank bleibt unverändert.
- Ein Lauf auf frischer Datenbank erzeugt keine Indexing-Fehler.
- README und `docs/sdd/handover.md` beschreiben die Kette, die Idempotenz, den
  Guard und den Probelauf.
- Voller `npm run check` grün (Surface `D`).

## Non-goals

Keine Migration, kein Docker-/CI-Umbau, kein automatischer Probelauf in CI
(der Wegwerf-Lauf bleibt ein manuelles Skript), keine Änderung an Produktdaten
oder Preisen.

## Known limits

- `scripts/rehearse-demo-setup.sh` kennt Port `5544` und den Namen
  `werkfaden_rehearsal`; es ist ein Prüfwerkzeug für diese Umgebung, kein
  generisches Werkzeug.
- Der Guard schützt nur die Skripte, die ihn aufrufen. Wer von Hand Produkte in
  eine fremde Datenbank schreibt, wird nicht aufgehalten.
- Die Kette ersetzt keine Daten: vorhandene Produkte mit gleichem Handle werden
  übersprungen, nicht aktualisiert.

## Checks / browser evidence

Rehearsal (frische Datenbank `werkfaden_rehearsal`): Lauf 1 und Lauf 2
`25 150 5 4 150 1 1` (Produkte, Varianten, Kategorien, Promotions, Bestände,
Regionen, Versandoptionen), 0 Fehlerzeilen in beiden Logs, 25 Dokumente im
Produktindex. Guard-Probe: `DATABASE_URL` der Dev-Datenbank mit
`DB_NAME=werkfaden_rehearsal` bricht mit "DATABASE_URL points at
\"werkfaden_dev\" but DB_NAME is \"werkfaden_rehearsal\"" ab; Dev-Datenbank
danach unverändert (25 Produkte, 1 Anfrage). Browser: nicht anwendbar — dieses
Ticket ändert keine Oberfläche.
