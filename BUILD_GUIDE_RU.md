## 0. Что мы строим (и что НЕ строим)

**Werkfaden** — немецкий интернет-магазин спецодежды (workwear) для маленьких
команд и частных покупателей. Это **учебно-портфолио проект** (Purpose:
`PORTFOLIO`, Tier: `Standard`) — демонстрация «клиентской» поставки, а не живой
бизнес.

Что должен уметь магазин (сценарий покупателя и оператора):

1. Покупатель ищет одежду, фильтрует по размеру/цвету/цене/наличию.
2. Открывает карточку товара, выбирает доступный вариант (размер + цвет),
   видит цену и наличие, посчитанные **на сервере**.
3. Кладёт в корзину, меняет количество; сервер сам отвергает нехватку товара.
4. Оформляет заказ с немецким адресом, видит товар + налог + доставку + итог.
5. Платит через **тестовый** Stripe (sandbox), получает заказ и историю заказов.
6. Отдельно может оставить **заявку на персонализацию** (нанести логотип) —
   оператор вручную её рассматривает; это НЕ покупка и не резерв товара.
7. Оператор через админку Medusa правит товары/остатки, обрабатывает заказы.

**Границы демо (жёстко):** нет реальных платежей, реальных писем (только
локальный «почтовый ящик»), реальных юр. данных, доставки/бухгалтерии
(POS/TSE/DATEV), маркетплейса, отзывов и т.п. Рабочее имя `Werkfaden` **не
проверено на товарный знак**. Все страницы явно помечены как демо.

**Язык:** магазин — `de-DE`. Валюта — `EUR`. Регион доставки — только Германия.

Почему это важно: любой текст, цена, срок — это фикция/шаблон, пока не
подтверждено владельцем. В коде и документации **нельзя** выдумывать факты.

## 1. Главная архитектурная идея

Проект — это **не** «написать интернет-магазин с нуля». Это официальный
монорепозиторий-стартер **Medusa DTC** (`medusajs/dtc-starter`), поверх которого
мы (1) настраиваем немецкий магазин, (2) пишем маленькую собственную фичу
(персонализация логотипа) и (3) собираем доказательства/тесты.

```
apps/backend/     — Medusa 2 (API-ядро + админка)          http://localhost:9000
apps/storefront/  — Next.js 15 витрина                     http://localhost:8000
docs/sdd/         — спека, контракт, тикеты, состояние
docs/content/     — контент-пакет (товары, тексты) + промпт
scripts/          — локальные setup-хелперы
compose.yaml      — изолированные PostgreSQL + Redis
```

**Ключевой принцип:** витрина (Next.js) только **показывает** данные и вызывает
мутации; всё денежное/складское считает Medusa (`services`/`workflows`). Цена,
налог, доставка, наличие, права — авторитет на бэкенде, браузер никогда не
источник истины. Нельзя вести вторую базу товаров/заказов.

Medusa = «движок коммерции»: у него из коробки есть корзина, чекаут, налоги,
склад, резервы, платежи, админка. Поэтому большинство фич — это **конфигурация**
и проверка, а не собственный код.

## 3. Локальное окружение (пререквизиты)

Нужно: Node 22.22.1 (`nvm use`), Docker (compose), pnpm. Если pnpm нет — можно
`npx --yes pnpm@10.11.1` вместо `pnpm`.

### Первый запуск (копипаст)

```bash
# 1. зависимости (строго по lockfile)
npx --yes pnpm@10.11.1 install --frozen-lockfile

# 2. сгенерировать секреты и .env приватно (откажется перезаписывать)
npm run setup:env          # создаёт .env, apps/backend/.env, apps/storefront/.env.local

# 3. поднять PostgreSQL + Redis
docker compose up -d --wait      # или: npm run infra:up

# 4. миграции БД
npx --yes pnpm@10.11.1 --filter @dtc/backend exec medusa db:migrate \
  --skip-scripts --execute-safe-links --execute-safe-search

# 5. магазин, поисковый индекс, каталог, склад, доставка/налог, промокоды
npm run setup:demo         # идемпотентно: повторный запуск ничего не дублирует

# 6. запуск
npm run backend:dev        # :9000  (админка :9000/app)
npm run storefront:dev     # :8000
```

### Про `.env`

- `scripts/setup-local-env.mjs` сам генерирует `WORKWEAR_DB_PASSWORD`,
  `JWT_SECRET`, `COOKIE_SECRET` и пишет три файла с правами `0600`. Он
  **специально отказывается** работать, если файлы уже существуют (чтобы не
  рассинхронизировать пароль БД). Секреты — только в gitignored-файлах.
- `apps/storefront/.env.local` содержит `NEXT_PUBLIC_MEDUSA_PUBLISHABLE_KEY`
  (пустой до `setup:store`), `NEXT_PUBLIC_MEDUSA_BACKEND_URL`,
  `NEXT_PUBLIC_DEFAULT_REGION=de`, `NEXT_PUBLIC_BASE_URL`,
  `NEXT_PUBLIC_STRIPE_KEY` (пустой до WW-006).
- Секреты **никогда** не печатать и не коммитить.

### Про Docker

`compose.yaml` поднимает Postgres (`werkfaden_dev`, юзер `werkfaden`, порт
`127.0.0.1:5544`) и Redis (`127.0.0.1:6384`). Оба слушают только localhost —
это НЕ прод-сервисы.

## 4. Рабочий процесс (как вообще делается каждый пункт)

1. Всё планирование — в `docs/sdd/`: сначала `intent.md` и `tier.md`
   (purpose + tier), затем `spec.md` (требования FR), `contract.md` (границы
   доверия, инварианты), потом нарезка на тикеты `docs/sdd/tickets/WW-XXX.md`.
2. Один тикет = одна ветка `feature/ww-XXX-<slug>` = один PR с описанием.
3. Перед PR: `npm run check` **зелёный** (lint + typecheck + unit + integration),
   для Astro/иных — ещё `build`.
4. Тикеты, которые трогают **авторизацию/платежи/загрузки файлов**, требуют
   свежего read-only ревью (двумя осями: Standards + Spec) **до** merge.
5. PORTFOLIO: агент мержит свой PR сам после зелёного check + ревью. CI в этом
   репо нет — воротник это `npm run check` + ревью.
6. `docs/sdd/state.md` — состояние (done / next / branch / env), 5–10 строк.
7. Conventional Commits, осмысленные сообщения. Не мержить фичи прямо в `main`.

Команды-воротник:

```bash
npm run check     # lint → typecheck → backend unit → storefront unit → integration
npm run build     # отдельно и обязательно перед релизом/bootstrap
```

## 5. Сборка по шагам: что уже сделано и как это делалось

Порядок тикетов не случаен: сначала контент и магазин, потом выбор товара,
корзина, оформление, платёж, аккаунты, админка, персонализация, легальщина.

### Шаг 0 — SDD-каркас

Создаёшь `docs/sdd/`: `intent.md`, `tier.md` (PORTFOLIO/Standard),
`spec.md` (FR-1…FR-14, NFR, UX), `contract.md` (границы доверия и инварианты),
`stack-decision.md` (почему Medusa DTC). Затем 11 тикетов `WW-000…WW-010`.
Это даёт «контракт» — дальше код пишется ровно под него, ничего лишнего.

### Шаг 1 — WW-000: контент-пакет и валидатор (`d8ee081`, PR #1)

Контент лежал в `docs/content/` и был сломан (битый JSON, противоречие про
SVG). Делаем:

- починить синтаксис `products.json`, `faq.json`, `ui.de.json`;
- убрать любые рекомендации грузить SVG/EPS (это stored-XSS риск; по NFR-S2
  разрешены только растр PNG/JPEG/WebP);
- схема + валидатор на Zod в `apps/backend/src/lib/content/` (fail-closed):
  25 товаров / 150 вариантов, уникальные SKU, согласованность цены/остатка;
- unit-тесты на всё это.
  Это **не** фича магазина, но без валидного контента нельзя сидить каталог.

### Шаг 2 — WW-001: стартер, БД, немецкий магазин (`811df1a`, PR #2)

`npm run setup:env` → `docker compose up` → миграции → `setup:store`
(регион Germany/EUR, sales channel, publishable key). Затем сид:
`src/scripts/seed-werkfaden-catalog.ts` создаёт 25 товаров / 150 вариантов,
коллекции, опции. Важный нюанс: **цены в Medusa v2 — в MAJOR units**
(`49.9` = €49,90), поэтому seed делит `price_gross_eur_cents` на 100.
Ещё `setup-inventory.ts` создаёт склад «Werkfaden Lager» и 150 inventory levels
(иначе фильтр «в наличии» бессмысленен).

### Шаг 3 — WW-002: каталог и фильтры (`01c7be4`, PR #12)

Байер ходит по категориям и фильтрует по размеру/цвету/цене/наличию; пустой
результат — понятное «Keine Artikel gefunden». Валидация query-параметров,
демо-баннер всегда виден. Урок: цены считать на сервере (major units), а не в
браузере.

### Шаг 4 — WW-003: карточка товара и варианты (`3fda05d`, PR #13)

Селектор всех комбинаций (размер × цвет); недоступные комбинации блокируются;
цена/наличие — с сервера; size-guide и материал — из `product.metadata`
(`size_guide`, `material`). URL обновляется `?v_id=…`. Есть unit-тесты
`variant-availability.unit.spec.ts` (accept/reject, частичный/полный выбор).

### Шаг 5 — WW-004: корзина (доставлена ядром, `1532f7e`, PR #14)

Решение: **не писать свой код**. Стартер уже даёт add/update/remove, а ядро
Medusa 2.21.2 само:

- проверяет наличие (сумма существующей строки + изменение) и отвергает
  превышение склада;
- отбрасывает неизвестные поля (например `unit_price`) и всегда берёт цену из
  pricing-модуля.
  Свой middleware на 21 тест был написан и **удалён** — он дублировал ядро.
  (Известные пределы ядра записаны в тикете: дробное количество, пустой
  `variant_id` → 500 и т.п.)

### Шаг 6 — WW-005: налог, доставка, итоги (`6b378ba`, PR #15)

`src/scripts/setup-checkout.ts` (идемпотентно, с guard на БД):

- налог-регион `DE_MWST_19` — 19%;
- **включён ли налог в цену** задаётся на уровне `currency_code=eur`
  price-preference (у каталожных цен нет region price-rule);
- fulfillment set «Werkfaden Versand» + зона «Deutschland», склад
  «Werkfaden Lager», способ доставки «Standardversand» — 5.90 EUR gross,
  правило `item_total >= 100` → 0.00 (бесплатно).
  Проверено live: 49.90/99.80 → 5.90, 149.70 → 0.00; граница 99.99 → 5.90,
  100.00 → 0.00. Немецкие тексты корзины/чекаута переведены.

### Шаг 7 — WW-009: персонализация логотипа (`8be09fd`, PR #16) — самая «наша» фича

Это единственная фича, которую мы писали как **собственный модуль**. Делаем так:

**Бэкенд** (`apps/backend`):

- `src/modules/personalization/` — модель `PersonalizationRequest` (статусы
  `submitted → reviewing → quoted / rejected → closed`), сервис, миграции;
- `lib/validation.ts` — Zod-поля с границами, определение формата по
  magic-bytes (`detectImageType`), карта переходов статусов, определение
  `customer_id` на сервере;
- `lib/image.ts` — проверка, что картинка реально декодируется (sharp);
- `src/workflows/create-personalization-request.ts` — проверяет, что вариант
  принадлежит товару, и создаёт запись (с компенсацией при ошибке);
- `src/workflows/update-personalization-request-status.ts` — проверяет
  допустимость перехода статуса (с откатом);
- `src/api/store/personalization-requests/route.ts` — публичное создание:
  multer берёт **один** файл, проверка размера ≤5 MiB и растра, загрузка в
  **приватное** хранилище со случайным именем; если сохранение упало — файл
  удаляется;
- `src/api/admin/personalization-requests/**` — только для админа: список,
  деталь, смена статуса, отдача файла (Content-Type берётся из сохранённого
  `logo_format`, не из URL);
- `src/lib/rate-limit.ts` + `middlewares.ts` — лимитер 5 запросов/мин на IP и
  перевод ошибок multer в 400 (иначе было бы 500);
- `apps/backend/src/modules/.../migrations/*` — таблица + колонка `logo_format`;
- `medusa-config.ts` — регистрация модуля и файлового провайдера
  (`@medusajs/file-local`).

**Витрина** (`apps/storefront`):

- `src/app/[countryCode]/(main)/personalization/page.tsx` — страница;
- `src/modules/personalization/components/personalization-form/index.tsx` —
  клиентская форма (выбор товара, количество, контакты, файл, обязательный
  чекбокс «права на логотип»);
- `src/lib/data/personalization.ts` — server action; multipart шлём **нативным
  fetch** (SDK JSON-сериализует тело);
- ссылки в шапке и в боковом меню.

**Проверки:** unit-тесты валидации/картинки/rate-limit; live-смок API
(201 / 400×3 / 429 / admin 401 / статусы / отдача файла); браузерный прогон
формы. Свежее ревью — обе оси APPROVE WITH NITS, блокеров нет.

### Шаг 8 — WW-006: платёж Stripe (план, ЗАБЛОКИРОВАН)

Нужно: подключить sandbox-провайдер `@medusajs/payment-stripe`, прописать ключи
(`sk_test` + `whsec` в `apps/backend/.env`, `pk_test` в
`apps/storefront/.env.local`), проверить: тестовый платёж создаёт **ровно один**
заказ, повторный/параллельный колбэк не плодит дубли, провалившийся платёж не
становится «оплаченным». Отдельный кастомный создатель заказов писать нельзя —
только штатный workflow ядра. **Ждём ключи от тебя.**

### Шаг 9 — WW-007: аккаунты и свои заказы (план)

Регистрация/логин/логаут + история заказов; чужой заказ/админ-операция
недоступны (проверка владения на бэкенде, не в браузере). Нужны reject-тесты.
Блокируется WW-006.

### Шаг 10 — WW-008: операции оператора (план)

Админ: править варианты (остаток/цена) и видеть это в витрине; выполнить/отменить
демо-заказ; поддерживаемый sandbox-refund; политика возврата товара на склад;
отказ в доступе без прав. В основном фронтенд админки. Блокируется WW-006.

### Шаг 11 — WW-010: демо-подача и легальность (план)

Локальные «письма» (Mailpit) с наблюдаемыми ошибками; немецкие Impressum/
Datenschutz (черновики с явными пробелами), демо-баннер; a11y/браузерные
проверки; README/handover/кейс. Блокируется WW-007/008/009.

## 7. Как менять внешний вид (visual)

Сейчас витрина использует **штатный дизайн стартера**: пресет `@medusajs/ui-preset`,
серая палитра `grey.0…grey.90`, скругления `soft/base/rounded/large/circle`,
шрифт **Inter**, часть анимаций в пресете. По решению проекта витрину начинаем
со стартерного дизайна, а **редизайн лендинга — отдельный поздний этап**.

### Правильный процесс изменения визуала

Когда захочешь «сделать красиво» или «как вот этот сайт»:

1. **Design intake.** Сначала вытащить направление в `docs/sdd/design.md`
   (токены: цвета, типографика, сетка, компоненты, моторика) — если проект
   новый/масштабная переделка. Показать тебе, дождаться **подтверждения**, и
   только потом кодить.
2. **Токены, а не хардкод.** Менять тему в `apps/storefront/tailwind.config.js`
   (`theme.extend.colors`, `fontFamily`, `borderRadius`, `screens`) и в
   `apps/storefront/src/styles/globals.css`.
3. **Компонентные классы.** Общие стили (например `.content-container`,
   `.contrast-btn`, типографика `.text-*-regular`) лежат в `@layer components`
   в `globals.css`. Правь их — не расползайся хардкодом по JSX.
4. **Один источник правды.** Не дублировать цвета/шрифты прямо в компонентах;
   только токены. `darkMode: "class"` уже включён.
5. **Проверка.** После смены темы прогнать `npm run check` и `npm run build`
   витрины, глазами проверить 360/768/1440 и отсутствие горизонтального скролла.

Точки входа для стилей и компонентов:

- `apps/storefront/tailwind.config.js` — палитра/шрифты/радиусы/screens/анимации;
- `apps/storefront/src/styles/globals.css` — базовые утилиты и `.text-*`,
  `.content-container`, кнопки;
- `apps/storefront/src/modules/**` — фичевые компоненты (layout, products,
  categories, cart, checkout, account, personalization и т.д.);
- `apps/storefront/src/app/**` — страницы App Router.

Правила из AGENTS: одна страница/«сделай как тут» → сначала извлечь направление
в `docs/sdd/design.md` и подождать подтверждения. Существующая дизайн-система
проекта побеждает. Мелкие правки дизайн-проход не требуют. Уважать
`prefers-reduced-motion`; тяжёлые анимации не нужны.

## 8. Подводные камни (gotchas), которые уже всплыли

- **Цены в major units.** `49.9` = €49,90. `lib/util/money.ts` `convertToLocale`
  НЕ делит на 100 — не «почини» его случайно.
- **Файловый модуль Medusa стателесс.** Нет таблицы `file`; «id файла» — это
  ключ провайдера (строка вида `private-<ts>-<uuid>.png`). Локальный провайдер
  `@medusajs/file-local` пишет приватные файлы в `static/` (в gitignore) —
  приватность только через admin-роут; в проде нужен S3.
- **`db:migrate` живёт только в корне.** Запуск: `pnpm -w run db:migrate`
  (у backend-пакета своего скрипта нет).
- **pnpm strict:** транзитивные зависимости не резолвятся сами — добавляй явно
  в `apps/backend/package.json` (так появились `@medusajs/file-local`, `multer`,
  `@types/multer`, `sharp`).
- **`medusa develop` спавнит дочерний `start`-процесс.** Правки оставляют
  осиротевшие дочерние процессы, дерущиеся за :9000. Убивай по явному PID
  (никогда `pkill -f`), перезапускай detached, лог →
  `/tmp/opencode/004-backend-dev.log`.
- **Next.js кэш:** storefront использует `force-cache`+tags; устаревшие данные
  переживают удаление `.next/cache`. Останови `next dev`, `rm -rf .next/cache`,
  запусти снова.
- **Мультипарт и SDK:** storefront `@medusajs/js-sdk` JSON-сериализует тело,
  поэтому загрузку файла шлём нативным `fetch` с `FormData`.
- **Multer по умолчанию** отдаёт 500 на свои ошибки — оборачивай в middleware
  и отдавай 400.
- **Zod 4 + TS-enum:** валидируй через `z.enum(Enum)`, а не string-union.
- **Zod strip unknown:** `z.object()` выкидывает лишние поля — именно так
  `customer_id`/`status` из тела запроса не проходят.
- **Известные ограничения стартера:** `/store` InstantSearch не работает (нет
  search-модуля, 404); интеграционный набор пуст (`integration-tests/http/` нет,
  `.env.test` нет); немецкие юр-страницы ещё не сделаны (WW-010).
- **`docs/` в этом репо tracked** (36 файлов) — в отличие от других проектов.
- **`docs/sdd` правки не попадут в PR**, если папка заигнорена в проекте — тут
  она как раз tracked, но следи.

## 9. Проверки и доказательства

```bash
npm run check     # lint + typecheck + backend unit + storefront unit + integration(empty)
npm run build     # backend medusa build + storefront next build
```

- `check` — строгий и **последовательный**; пустые наборы помечены
  `--passWithNoTests`, но это видимая заглушка, а не «зелёный релиз».
- Тесты НИКОГДА не идут в прод/дев-БД; интеграционные — только в отдельную
  тестовую БД с guard'ом (харнесс ещё не поднят — это известный пробел).
- UI-сценарии и находки ревью — это **доказательства** (live-смок, браузер),
  не просто число зелёных unit-тестов.
- Незакрытые вещи, отсутствующие креды и пропущенные проверки фиксируются в
  `state.md` / `handover.md`.

Полезные факты для ручных проверок:

- publishable key берётся из `apps/storefront/.env.local` (dev-ключ был
  `pk_06420…` — не публикуй).
- админ-логин создаётся через `medusa user` (в dev был
  `test-admin@werkfaden.local` — локальный, не в репо).
- БД напрямую: `docker exec werkfaden-postgres-1 psql -U werkfaden -d werkfaden_dev`
  (роли `postgres` нет; unix-socket trust).

   Нажал вторую кнопку -> Клиенту ушло письмо с трек-номером.
   Возвраты и кредит-ноты (Gutschriften) создаются в пару кликов.
5. 📱 Мобильное приложение (Shopware Admin App)
   У Shopware есть официальное мобильное приложение. Владелец бизнеса может:
   Смотреть дашборд с продажами в реальном времени (сидя в кафе или в отпуске).
   Обрабатывать новые заказы и печатать инвойсы прямо с телефона.
   Отвечать на сообщения от клиентов.
6. 🇩🇪 Полная локализация
   Админка идеально переведена на немецкий язык. Все юридические термины, кнопки и настройки соответствуют немецким реалиям (DSGVO, AGB, Widerrufsrecht). Клиенту не придется гадать, что значит та или иная настройка.
   ⚠️ Что клиент НЕ сможет делать (Где нужны ВЫ)
   Чтобы вы понимали границу между зоной ответственности клиента и разработчика:
   Обновление ядра и плагинов: Клиент нажимает кнопку "Обновить", но если что-то сломается (конфликт плагинов), чинить это должны вы.
   Установка новых интеграций: Подключить новую ERP-систему (например, JTL-Wawi) или специфический платежный шлюз — это ваша задача.
   Глобальные изменения дизайна: Если клиент скажет "Я хочу, чтобы корзина выезжала справа, а не открывалась отдельной страницей, и шрифт был другой" — это требует вмешательства разработчика (Twig/Vue.js/CSS).
   Настройка сервера: Бэкапы, оптимизация скорости (ElasticSearch, Redis), безопасность — это ваша зона ответственности.
   Итог для вашего бизнеса:
   Shopware 6 снимает с вас рутину.
   Вы, как разработчик, один раз настраиваете фундамент, подключаете платежи (Mollie/PayPal), логистику (DHL) и настраиваете базовую тему.
   После этого вы передаете ключи клиенту. Он сам наполняет каталог, сам запускает промо-акции, сам меняет баннеры к праздникам. Вы остаетесь на "технической поддержке" (Wartungsvertrag) — берете с него фиксированную сумму (например, 150-300 евро в месяц) за бэкапы, обновления сервера и мелкие доработки, которые он не может сделать мышкой.
   Это идеальная модель для работы с малым и средним бизнесом в Германии. Клиент счастлив (у него мощная, красивая админка), а вы не тратите время на ручное добавление товаров.

Этот стек (Shopware 6 Headless + Next.js + AI) — это уровень Enterprise / Premium-агентств. Если ты сможешь это грамотно реализовать и задеплоить, ты будешь стоить на рынке Германии не 50k, а 90k+ евро в год, или сможешь брать за один такой проект от 15 000 до 40 000 евро.
Но Headless-архитектура кардинально меняет подход к хостингу. У тебя больше не просто "один сервер с сайтом". У тебя распределенная система: Бэкенд (PHP/MySQL), Фронтенд (Node.js/Edge), БД векторов (для AI), Очереди (RabbitMQ) и Поиск (Elasticsearch).
Главное правило для Германии: DSGVO (GDPR). Данные немецких клиентов обязаны физически храниться на серверах в Евросоюзе (в идеале — в Германии). Иначе ты получишь иск.
Ниже подробный разбор того, куда это деплоить и сколько это будет стоить в месяц для малого/среднего бизнеса.
🏗 Архитектура деплоя (Где что размещать)
Тебе нужно разделить систему на три независимых контура. Это даст невероятную скорость и надежность.

1. Бэкенд (Shopware 6 Core + API + MySQL + Elasticsearch)
   Что это: "Мозги" магазина. Генерирует JSON для фронта, хранит заказы, работает с платежами.
   Требования: Shopware 6 + Elasticsearch очень прожорливы до оперативной памяти (RAM). Нужно минимум 8-16 ГБ RAM.
   Куда деплоить: Только VPS или Dedicated Server в Германии.
   🏆 Hetzner (Германия) — абсолютный стандарт в немецком IT. Дешево, невероятно быстро, 100% соответствие DSGVO.
   Netcup / IONOS — хорошие альтернативы.
2. Фронтенд (Next.js / Nuxt.js PWA)
   Что это: Визуальная часть, которая общается с Shopware через Store API.
   Куда деплоить: Edge-сети или Node.js хостинг.
   Vercel / Netlify (выбирай регион EU). Очень просто, автоматический CI/CD, мгновенный деплой. Нюанс: строгие немецкие юристы иногда придираются к IP-маршрутизации Vercel, нужно правильно настроить DPA (Data Processing Agreement).
   🏆 Cloudflare Pages (EU) или Coolify на том же Hetzner (Self-hosted). Cloudflare идеален для PWA и кэширования статики, а Coolify позволит тебе хостить Next.js на твоем сервере в Германии без переплат.
3. AI и Микросервисы (Чат-боты, Рекомендации, Векторные БД)
   Куда деплоить: SaaS-решения с серверами в ЕС или отдельные Docker-контейнеры.
   OpenAI API / Mistral (для генерации текстов) — API-вызовы.
   Vector DB (Pinecone / Qdrant / Weaviate) — для хранения "смыслов" товаров (нужно для умного AI-поиска и рекомендаций).
   Чат-бот (Tidio, Intercom или open-source Chatwoot).
   💰 Калькулятор затрат (Ежемесячно для клиента)
   Давай посчитаем реальный бюджет, который ты должен заложить в коммерческое предложение для клиента (TCO - Total Cost of Ownership).
   Вариант А: "Оптимальный / Profitable" (Hetzner + Vercel + SaaS)
   Идеально для малого/среднего бизнеса. Баланс цены и скорости.

   🤖 Как работают затраты на AI (Важно объяснить клиенту)
   Клиенты боятся, что "Искусственный Интеллект" будет стоить тысячи евро. Тебе нужно объяснить им разницу между разовыми и постоянными тратами:
   AI-генерация описаний товаров (Разовая трата):
   У клиента 1000 товаров. Ты пишешь скрипт, который через OpenAI API генерирует SEO-описания на немецком с учетом тональности бренда.
   Затраты: Сгенерировать 1000 качественных описаний через GPT-4o стоит около 5-10 евро один раз. Дальше текст хранится в базе Shopware бесплатно.
   AI-персонализация и Рекомендации (Постоянная трата):
   Чтобы советовать товары ("С этим покупают..."), ты будешь отправлять события (User X купил Y) в Vector Database (например, Qdrant).
   Затраты: Для магазина с 10 000 заказов в месяц это будет стоить около 10-20 евро в месяц за хостинг базы и API-запросы.
   Чат-бот поддержки (Постоянная трата):
   Бот, обученный на PDF-инструкциях и AGB магазина.
   Затраты: Можно взять готовый SaaS (Tidio) за ~25 €/мес, или захостить Open-Source Chatwoot на том же Hetzner за 0 € (платишь только копейки за токены OpenAI).
   🛠 Как тебе это администрировать (Твоя головная боль)
   Если ты выбираешь Вариант А (Hetzner), тебе нужно управлять Linux-сервером. Shopware 6 требует настройки Nginx/Apache, PHP-FPM, Redis, MySQL, Elasticsearch, RabbitMQ и Cron-задач.
   Твой секретный инструмент: Coolify или Docker Compose.
   Не настраивай сервер руками через консоль. Используй Coolify (это open-source альтернатива Vercel/Heroku, которую ты ставишь на свой Hetzner VPS).
   Ты подключаешь GitHub к Coolify.
   При git push Coolify сам собирает твой Next.js фронтенд и деплоит его.
   Shopware 6 ты упаковываешь в Docker-контейнеры (есть готовые официальные образы Shopware Docker).
   В итоге ты получаешь Enterprise-деплой пайплайн за 35 евро в месяц, и все данные физически лежат в Германии на твоем сервере. Юристы клиента будут в восторге.
   🚀 Как это продавать немецкому бизнесу (Твое УТП)
   Когда ты придешь к немецкому клиенту (например, к производителю мебели или бренду одежды) с этим стеком, ты говоришь не "я сделаю вам магазин". Ты продаешь Business Value:
   "Мы сэкономим вам 40 часов в месяц на контенте"
   Как: AI сам напишет описания для 50 новых товаров, сам переведет их на английский и французский (для рынка ЕС), сам сгенерирует Alt-теги для картинок.
   "Скорость загрузки как у Amazon (Core Web Vitals)"
   Как: Next.js PWA на Edge-сети загружается за 0.4 секунды. Google обожает такие сайты и дает им ТОП-1 в поиске. Конверсия на быстрых сайтах в Германии выше на 20%.
   "Мы повысим средний чек (AOV) на 15%"
   Как: AI-рекомендации будут анализировать поведение пользователя в реальном времени и подсовывать именно те товары, которые он реально хочет купить, а не просто "популярное".
   "100% Безопасность и DSGVO"
   Как: "Мы не используем американские облака. Ваш сервер стоит во Франкфурте, данные клиентов не покидают Германию, Cookie-баннер интегрирован с бэкендом".
   Резюме:
   Затраты на инфраструктуру для такого "Монстра" составят для клиента смешные 120-150 евро в месяц. Это в 3-4 раза дешевле, чем Shopify Plus, но дает функционал, которого в Shopify нет из коробки (кастомные AI-модели, сложная B2B логика). Твоя задача как разработчика — упаковать Shopware в Docker, поднять Next.js и грамотно связать их через Shopware Store API. Это сделает тебя элитой на рынке e-commerce.
