# WW-021: Two operator decisions cannot overwrite each other

Status: in progress (branch `fix/ww-021-quote-status-race`).

Surface: `B` (quote module, workflow, integration spec).

## Intent / delivers

Closes the quote-status finding of the 2026-10-25 review.

Accepting a quote was already a compare-and-set, but every operator transition
(`quoted`, `rejected`, `closed`) was a read-then-write:
`retrieveQuoteRequest` → `canTransition` → `updateQuoteRequests`. Two decisions
that overlapped both validated the status they had read, and the later write
won. The visible damage: a buyer accepts (row `accepted`, promotion code issued)
while an operator rejects the same quote; the reject writes over it, and the
shop holds a `rejected` quote whose code is still live for a week.

`src/modules/quote/lib/status.ts` adds `transitionQuoteStatus`, an
`update … where id = ? and status = ?` compare-and-set that also writes the
offer fields, so a rollback can restore the previous offer instead of clearing
it. The step now writes through it and answers
`NOT_ALLOWED` ("This quote changed in the meantime.") when it lost. The
compensation reverses through the same CAS.

## Blocked by

Nothing. WW-013 built the transitions, WW-016 built the accept-side CAS.

## Verification scenario

GIVEN a submitted quote and two operator decisions that overlap in time WHEN
both run THEN exactly one answer is 200, the row carries the decision that won,
and the loser is told to reload; and GIVEN a quoted quote WHEN a buyer's accept
and an operator's reject overlap THEN the row matches the winner and a code
exists only if the accept won.

## Acceptance criteria

- `transitionQuoteStatus` is the only writer of `quote_request.status` from
  operator routes; the accept path keeps its own CAS in `acceptance.ts`.
- The status written is conditioned on the status that was validated; a lost
  race raises `NOT_ALLOWED`, no field of the losing decision is applied.
- New integration spec `ww-021-quote-status-race.spec.ts`: quote-vs-reject on a
  submitted quote, accept-vs-reject in both start orders (row lock held while
  both writers block on it), rejected-then-accept is refused, and the
  promotion count matches the winner.
- Existing quote, acceptance and admin specs stay green; full `npm run check`
  green (surface `B`).

## Non-goals

No new statuses, no optimistic-concurrency column on the model, no admin UI
conflict handling beyond the error message, no change to the discount
mechanism (that wording is WW-022).

## Known limits

- `NOT_ALLOWED` reaches the admin dashboard as a 400 with the message; Medusa's
  admin UI shows it as a generic failure, an operator has to reload to see the
  current status.
- The lock in the spec is held on the quote row, so the specs prove the CAS
  under a real Postgres lock rather than under a mocked one. They still cannot
  prove fairness of the winner: both start orders are covered instead.
- The reject that loses still writes nothing but its workflow event is emitted
  only for the winner; no "conflict" metric exists.
