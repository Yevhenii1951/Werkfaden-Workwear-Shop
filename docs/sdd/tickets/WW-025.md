# WW-025: Zahlung und letzter Bestand sind gegen Doppelabruf gefestigt

Status: in progress (branch `test/ww-025-payment-idempotency`).

Surface: `B` (`apps/backend`).

## Intent / delivers

Zwei Zusagen des Shops waren bisher nur für den gutwilligen Ablauf belegt:

- **Letzter Bestand:** `ww-006` prüft den Fall nacheinander — erst kauft A, dann
  B. Dass auch zwei *gleichzeitige* Abschlüsse nur einen Gewinner ergeben und
  der Lagerstand nicht negativ wird, war nicht getestet.
- **Doppelte Zahlungsereignisse:** `ww-006` prüft, dass ein wiederholter
  `complete`-Aufruf dieselbe Bestellung zurückgibt. Für ein wiederholt
  eintreffendes Zahlungsereignis (Webhook) gab es keinen Beleg.

Geliefert: `integration-tests/http/ww-025-payment-idempotency.spec.ts` mit zwei
Tests — paralleler Abschluss um die letzte Einheit und wiederholte
Zahlungsereignisse (sequenziell und parallel) — mit Zählung der Bestellungen und
Zahlungen in der Datenbank.

## Abgrenzung: was hier nicht getestet wird

Die Signaturprüfung des Webhooks und das Übersetzen des Stripe-Events in eine
Aktion (`authorized` / `captured` / …) gehören dem Provider, nicht diesem
Projekt: `@medusajs/payment-stripe` prüft die Signatur mit
`constructEvent` und liefert die Aktion über `getWebhookActionAndData`
(installierte Quelle: `dist/core/stripe-base.js`). Ein echter signierter
Stripe-Request wäre in diesem Test nur mit dem Stripe-Client und einem
Netzwerkaufruf zu erzeugen.

Getestet wird der Teil, den dieses Projekt verantwortet: dass dasselbe
Zahlungsereignis mehrfach verarbeitet werden darf, ohne eine zweite Bestellung
oder Zahlung zu erzeugen — über den Workflow, den der Webhook-Subscriber
aufruft.

## Verification scenario

GIVEN eine letzte Einheit von Artikel X und zwei Warenkörbe mit je einer Einheit
WHEN beide Abschlüsse gleichzeitig laufen
THEN endet genau einer mit einer Bestellung und genau einer mit einem Fehler,
es gibt genau eine Bestellung, und `stocked_quantity` bleibt ≥ 0, während
`reserved_quantity` die verfügbare Menge nicht übersteigt.

GIVEN ein abgeschlossener Kauf
WHEN dasselbe Zahlungsereignis (gleiche Session, gleicher Betrag) noch einmal
und dann zweimal gleichzeitig verarbeitet wird
THEN bleiben genau eine Bestellung und genau eine Zahlung bestehen.

## Acceptance criteria

- Beide Tests laufen im normalen `npm run check` mit (Integration, letzter
  Schritt).
- Der Bestandstest schlägt fehl, wenn beide Abschlüsse durchgehen (also
  mindestens zwei Bestellungen entstehen) — nachgewiesen, nicht behauptet.
- Kein Produktionscode geändert, außer wenn ein Test einen echten Fehler zeigt;
  dann steht der Fix in diesem Ticket und der Test ist sein Beweis.
- `npm run check` grün.

## Non-goals

Keine neuen Abhängigkeiten, kein echter Stripe-Webhook-Aufruf, keine Änderung an
Provider-Konfiguration, keine Lasttests.

## Known limits

- Der Parallelitätstest nutzt zwei gleichzeitig abgeschickte HTTP-Aufrufe im
  selben Prozess; ein verteilter Aufruf über mehrere Instanzen ist damit nicht
  abgedeckt.
- Die Reihenfolge der beiden Ereignisse ist nicht bestimmt; geprüft wird das
  Ergebnis, nicht der Weg.

## Checks / evidence

Die Spec allein (`TEST_TYPE=integration:http`, nur diese Datei):

| Test | Ergebnis |
| --- | --- |
| letzte Einheit, zwei gleichzeitige Abschlüsse | bestanden: genau ein 200 mit Bestellung, genau ein 400, eine Bestellung, `stocked_quantity` 0 |
| dasselbe Zahlungsereignis zweimal nacheinander und zweimal gleichzeitig | bestanden: eine Bestellung, eine Zahlung |

**Gegenprobe, damit der Test nicht nur zufällig grün ist:** mit zwei Einheiten
im Lager dürfen beide Käufer gewinnen — genau dann muss der Test scheitern. Mit
dieser Änderung (temporär, nicht committet) schlug er fehl wie erwartet:
`Expected length: 1, Received length: 2` — beide Abschlüsse endeten mit 200.
Damit ist belegt, dass die Zusicherung „genau ein Gewinner“ wirklich prüft und
dass beide Anfragen im selben Zeitfenster laufen.

Voller `npm run check`: Ergebnis im PR.
