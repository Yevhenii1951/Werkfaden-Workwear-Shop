# WW-026: Kontodaten kommen nicht aus dem gemeinsamen Cache

Status: in progress (branch `fix/ww-026-account-no-store`).

Surface: `S` (`apps/storefront`).

## Intent / delivers

`retrieveCustomer`, `retrieveOrder` und `listOrders` lasen mit
`cache: "force-cache"`. Das heißt: die Antwort bleibt im Datencache, bis ein
Tag sie verwirft oder sie verdrängt wird — nicht bis sich die Daten ändern.

Der naheliegende Verdacht — ein Konto könnte die Daten eines anderen aus dem
Cache bekommen — trifft **nicht** zu. Next nimmt die Header in den
Cache-Schlüssel auf
(`apps/storefront/node_modules/next/dist/server/lib/incremental-cache/index.js`,
`generateCacheKey`: nur `traceparent`/`tracestate` fliegen raus), und das
`authorization`-Header unterscheidet sich pro Konto.

Was übrig bleibt, ist Veraltung — und sie ist nicht überall gleich groß:

- `customers` wird bei Login, Logout, Profil- und Adressänderung revalidiert.
  Das passt.
- `orders` wird nur an einer Stelle revalidiert: in `placeOrder`
  (`cart.ts`), also nach einem eigenen Kauf. Die Bestellliste ist damit aktuell.
- **`retrieveOrder` hat denselben Tag, aber keine Invalidierung für alles, was
  von außen kommt:** der Zahlungs-Webhook, eine Stornierung, ein
  Fulfillment-Schritt. Die Bestellseite und die Bestätigungsseite zeigen dann
  den Stand, der beim ersten Aufruf im Cache lag — bis der Eintrag verdrängt
  wird.

Geliefert: die drei kontobezogenen Reads laufen mit `cache: "no-store"` und ohne
Cache-Tags; die damit nutzlos gewordenen `revalidateTag`-Aufrufe für
`customers` entfallen. Katalog-, Warenkorb- und Region-Lesevorgänge bleiben
unverändert gecacht.

## Complexity

| Axis | Value | Why |
| --- | --- | --- |
| Implementation | low | drei Fetch-Optionen, ein paar tote Zeilen |
| Verification | medium | Cache-Wirkung ist nur mit Produktionsbuild und Zählung der Backend-Aufrufe belegbar |

## Context to read

Dieses Ticket + `../contract.md` (Abschnitt Cache/Tags) +
`apps/storefront/src/lib/data/{customer,orders,cookies}.ts`.

## Verification scenario

GIVEN ein eingeloggtes Konto und ein Produktionsbuild WHEN `/de/account`
zweimal aufgerufen wird THEN fragt die Storefront den Backend-Endpunkt
`/store/customers/me` bei **jedem** Aufruf (vorher: nur beim ersten). Dasselbe
für `/de/account/orders` und `/store/orders`.

## Acceptance criteria

- `retrieveCustomer`, `retrieveOrder`, `listOrders` nutzen `no-store` und keine
  Tags.
- Kein `revalidateTag("customers…")` bleibt übrig, das nichts mehr trifft.
- Katalog, Warenkorb, Regionen und Checkout bleiben unverändert gecacht und
  `npm run check` bleibt grün.
- Login, Logout, Profiländerung und Bestellansicht funktionieren im Browser.

## Non-goals

Kein Umbau des Cache-Konzepts der Storefront, keine Änderung an
Warenkorb-Caching, keine neue Abhängigkeit, keine Sitzungsverwaltung.

## Known limits

- Ein `no-store` kostet pro Aufruf einen Backend-Request; bei einer
  Kontoseite mit wenigen Aufrufen ist das der richtige Tausch.
- Der Beweis gilt für den gebauten Stand; im Dev-Server ist der Datencache
  ohnehin nicht repräsentativ.

## Checks / browser evidence

Gezählt wurden die Backend-Aufrufe im Medusa-Log, jeweils Produktionsbuild
(`npm run build:ui` + `next start`), eingeloggt als ein Testkonto, je drei
Aufrufe von `/de/account` und drei von `/de/account/orders`:

| Stand | `GET /store/customers/me` | `GET /store/orders` |
| --- | --- | --- |
| vorher (`force-cache`, `main`) | 1 | 1 |
| nachher (`no-store`) | 6 | 6 |

Vorher diente also eine einzige Antwort für alle drei Seitenaufrufe, nachher
fragt jeder Aufruf das Backend (zwei pro Seitenaufruf: Layout und Seite rendern
getrennt). Die Seiten selbst bleiben korrekt: Konto zeigt das angemeldete
Konto, Bestellliste lädt, Login/Logout funktionieren im Browser.

`npm run check:ui` (4 Suiten / 34 Tests), `npm run build:ui` (41 Seiten) und der
volle `npm run check`: Ergebnisse im PR.
