# WW-013: B2B quote requests (RFQ → offer → checkout)

Status: open.

## Intent / delivers

First slice of FR-14 "quote acceptance/payment": a business buyer requests a
quote for items and quantities, the operator answers with a net price, the
buyer accepts and pays through the existing sandbox checkout. Negotiation is
delivered on top of core commerce primitives, never beside them:

- Custom module `quote` (same pattern as `personalization`): QuoteRequest
  with customer relation (optional), company name, contact data, line items
  (variant + quantity), bounded comment, status, timestamps.
- Status flow: `draft → submitted → quoted → accepted | rejected → closed`,
  operator-only transitions, explicit transition map with reject tests.
- Money path: on `quoted` the operator enters a total; acceptance issues a
  **single-use, short-TTL promotion code** for that amount (core Promotion
  module), which the buyer applies in the normal cart/checkout (WW-012 UI).
  No parallel order creator, no custom payment handling — Stripe sandbox and
  core order workflow stay authoritative (contract.md).
- Storefront: `/angebote` (list + detail for the customer, ownership-
  enforced), request form prefilled from cart, accept → code revealed →
  redirect to checkout. Admin: list/detail/status routes under
  `/admin/quotes` + file-free operator note field.

## Blocked by

WW-012 (buyer applies the offer code through the discount-code UI).

## Complexity

Implementation: high. Review: high — auth/ownership + money; fresh read-only
security review required before merge.

## Context to read

This ticket + ../contract.md + ../state.md + WW-009 (module pattern) +
WW-012 (promotion application). Official docs for Promotions before coding.

## Verification scenario

GIVEN an authenticated and an anonymous buyer WHEN they submit quote requests
THEN each sees only their own; GIVEN a quoted request WHEN the buyer accepts
THEN a single-use code covering the offer is issued, applies once in checkout
and produces a correct paid order; WHEN a second use, a foreign quote or a
rejected quote is attempted THEN it is denied server-side.

## Acceptance criteria

- Module + migration; Zod validation at every custom endpoint; rate limit on
  public submission; ownership checks mirror WW-007.
- Offered total is operator-entered but validated (positive, within the
  region currency, not below a documented floor); the promotion code derives
  its amount server-side from the stored offer, never from client input.
- Integration tests on the test DB: submission, ownership rejects, transition
  map rejects, code issuance, single-use enforcement, code + checkout →
  correct order totals. Browser evidence for the buyer path in German.
- `npm run check` green; fresh read-only review recorded in the PR.

## Non-goals

No company accounts with multiple users, no negotiated price lists /
customer-group tiers (next slice of FR-14), no repeat ordering, no file
attachments on quotes, no quote PDF export.

## Checks / browser evidence

Buyer: cart → "Angebot anfordern" → submit → operator quotes (API/admin) →
accept → code → checkout → order. Negative: second code use, foreign quote
detail URL.
