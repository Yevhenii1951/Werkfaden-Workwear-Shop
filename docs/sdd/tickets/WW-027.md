# WW-027: Search index learns about option edits

Status: in progress (branch `fix/ww-027-option-search-ids`).

Surface: `B` (search index helper, integration spec).

## Intent / delivers

Found while rehearsing a from-scratch setup for WW-023: on a fresh database the
catalog seed prints two indexing errors per product.

The product index maps events of other entities back to the products behind
them. For options it was reading columns that do not exist: `product_option`
has no `product_id` (the relation is the `product_product_option` link), and a
`product_option_value` reaches its option, not its product. `query.graph`
therefore answered with `null` rows, and the helper dereferenced them:

```
Processing product-option.created which has 1 subscribers
Cannot read properties of undefined (reading 'product_id')
```

Every option or option-value change crashed the indexer instead of reindexing
the affected products, so an option rename never reached the search document.
The option-value case failed quietly: the row resolved, the field did not,
so the result was an empty id list.

The helper now reads `products.id` (option) and `option.products.id` (option
value), and skips rows the graph could not resolve instead of dereferencing
`null`. A new integration spec drives the shipped helper against a real product
with one option and one value.

## Blocked by

Nothing. WW-023 only surfaced it.

## Complexity

| Axis | Value | Why |
| --- | --- | --- |
| Implementation | low | two field paths, one null filter |
| Review | medium | the failure is a log line plus a silently stale document |

## Context to read

This ticket + ../contract.md (search index). Medusa facts used, verified against
the installed 2.21.2 packages and a live `query.graph`: options and option
values are linked to products through link tables, so the graph path is
`products.id` / `option.products.id`; an unresolvable path yields `null` rows
rather than an error.

## Verification scenario

GIVEN a product with one option and one value WHEN the index receives
`product-option.created` or `product-option-value.created` THEN the helper
returns that product id; and GIVEN `product.created` THEN the id passes through
unchanged.

## Acceptance criteria

- `resolveProductIds` maps option and option-value events to their products.
- Unresolvable graph rows are skipped; no event path throws.
- New integration spec `ww-027-search-option-ids.spec.ts` (3 tests); it fails on
  the previous helper and passes on the new one.
- Full `npm run check` green (surface `B`).

## Non-goals

No change to the index definition, the document shape, the seeding strategy or
the `product-tag` / `product-category` paths (verified working in a rehearsal
database). No new search feature.

## Known limits

- The spec asserts the mapping, not the rendered document: the subscriber that
  calls it also needs a ready index, which the search spec (WW-011) already
  covers.
- A tag is only indexed through `products.id`; that path was verified by hand in
  a rehearsal database, not pinned by a test — the demo catalog has no tags.

## Checks / browser evidence

`npm run check` (backend unit + integration incl. the new spec). Browser: not
applicable — no UI change. Rehearsal evidence: the from-scratch setup no longer
logs an indexing error while seeding.
