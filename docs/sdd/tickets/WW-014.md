# WW-014: Embroidery price calculator

Status: open.

## Intent / delivers

Last slice of FR-14 "automated embroidery pricing": a buyer gets a
deterministic server-calculated surcharge estimate for embroidering a logo on
a chosen item before ordering. The calculator is a **quoting aid, not a paid
add-on** — it feeds the personalization/quote flows rather than the cart.

- Backend: pure pricing function (module `embroidery` or a lib next to the
  quote module): inputs = position (chest/back/sleeve), stitch-count band,
  quantity band, garment category; output = unit surcharge + total in EUR,
  rounded per documented German retail rule. All rates live in one explicit
  table in code (demo rates, documented as fixtures — no invented "market
  prices" claims). Zod-validated store endpoint
  `POST /store/embroidery/estimate`, rate-limited, no auth required.
- Storefront: estimator UI on the personalization page (or `/stickerei`):
  select product, position, stitch band, quantity → server-derived estimate
  with a clear "unverbindliche Schätzung" disclaimer; CTA sends the chosen
  configuration into a personalization request (WW-009) or quote request
  (WW-013) with prefill — the estimate itself never becomes a cart line item.
- Tests: unit tests own the rate table boundaries (band edges, rounding, zero
  and max quantities, unknown position rejected); integration test covers the
  endpoint's validation rejects and a happy path.

## Blocked by

WW-013 for the "send configuration into a quote request" CTA (the estimator
itself and personalization prefill only need WW-009, already merged).

## Complexity

Implementation: medium. Review: medium (pricing logic must be
server-authoritative; no security-sensitive paths).

## Context to read

This ticket + ../contract.md + ../state.md + WW-009 + WW-013.

## Verification scenario

GIVEN the estimator WHEN valid inputs are posted THEN the server returns the
surcharge from the rate table and the storefront renders it with the
disclaimer; WHEN inputs are outside the bands or malformed THEN a validation
error is returned and no price is shown.

## Acceptance criteria

- Rate table and rounding rule documented in the PR and near the table;
  values labelled demo fixtures.
- Estimate is computed server-side only; the client never sends a price.
- Disclaimer text in German on the UI; reduced-motion-safe interaction.
- Unit + integration coverage as above; `npm run check` green; fresh
  read-only review in the PR.

## Non-goals

No real embroidery partner integration, no CAD/stitch-file upload, no
automatic quote generation, no changes to cart/inventory, no multi-position
bulk discount engine (bands cover quantity only).
